## 0. The short version

1. Happy has **two generations**. The original CLI (`happy-cli`, ~23k lines of harness code) wraps other people's agents one by one: Claude Code through the Agent SDK, Codex through `codex app-server` JSON-RPC, Gemini/OpenCode/anything through the Agent Client Protocol (ACP), Antigravity (`agy`) through plain-text stdout, and OpenClaw through its own WebSocket gateway. Happy Agent (`happy-agent-runtime`) is a **new harness of its own** ("built on Pi" by its README, though no Pi package is in its lockfile) with its own tool sets and prompts per vendor. It reaches Claude through the Claude Code binary inside the Agent SDK (`permissionMode: "dontAsk"`, `tools: []`), and reaches Codex and Grok through **re-implemented API clients** that read the vendor CLI's token file, send the CLI's own identity headers (`originator: codex_exec`, `grok-shell/1.0.46`) to `chatgpt.com/backend-api/codex` and `cli-chat-proxy.grok.com`, and refresh those tokens themselves. The vendor harnesses (Claude Agent via ACP, Codex app-server) are optional "foreign agents". The README line "Orchestrate Claude, Codex and Grok in one app" describes this second generation (§2).
2. **Permission prompts are the same shape everywhere in Happy**: a map `agentState.requests[id] = { tool, arguments, createdAt }` on the session, answered by an RPC `permission { id, approved, decision?, mode?, allowTools? }`. Each harness adapter translates that into its own vocabulary (`canUseTool` → `{behavior}`; Codex → `accept|acceptForSession|decline|cancel`; ACP → `optionId`). This is exactly a parked Steward `Approval` + `POST /api/approvals/:id/decision` (§1.6).
3. The **Codex app-server** client (1,584 lines) and the **Claude permission handler** (457 lines) are the two pieces worth reading closely. Both are hand-rolled because the official SDKs do not expose approvals: `@openai/codex-sdk` only wraps `codex exec`, and `@ag-ui/claude-agent-sdk` never wires `canUseTool`.
4. **ACP is real now.** `@agentclientprotocol/sdk` 2.0.2 (Apache-2.0) on npm; 48 agents listed on agentclientprotocol.com including Gemini CLI (native), Codex (`@zed-industries/codex-acp` 0.16.0), Claude Agent (`@zed-industries/claude-agent-acp` 0.23.1), GitHub Copilot, Pi, OpenClaw, OpenCode, Goose, Cursor. Its `session/request_permission` carries options with `kind ∈ allow_once | allow_always | reject_once | reject_always` and a `ToolKind` (`read | edit | delete | move | search | execute | fetch | think | other`), which maps cleanly onto Steward's `ToolKind` and `ApprovalAnswer`. Happy ignores the `kind` field; Steward should not.
5. Happy's own normalised vocabulary (`happy-wire/src/sessionProtocol.ts`, 174 lines) is nine event kinds inside an envelope. Its header says it is "UNDER REVIEW", frozen, and that the authors want to align with Pi's protocol instead. It is a strict subset of AG-UI; every kind has a direct AG-UI event, and AG-UI additionally has `SUBAGENT_STARTED/FINISHED/ERROR`, `subagentRunId`, `TokenUsage[]` on `RUN_FINISHED`, and the interrupt outcome Steward already uses. External harnesses should arrive in Steward as AG-UI agents; there is no reason to adopt Happy's envelope.
6. **Subscriptions**: the vendor terms are the hard constraint, not the code. Anthropic's legal page (fetched 27 Oct 2026) says OAuth is "intended exclusively" for "ordinary use of Claude Code and other native Anthropic applications", that Agent SDK developers "should use API key authentication", and that third parties may not "route requests through Free, Pro, or Max plan credentials on behalf of their users" nor "collect, store, or intermediate Claude.ai credentials or session tokens". OpenAI's app-server page says "App-server authentication has never been permitted for commercial or hosted services" and recommends "Sign in with ChatGPT" for "local or open-source apps". Anthropic's support article "Use the Claude Agent SDK with your Claude plan" (cited by Happy) says the opposite in part: "Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription limits" (15 June 2026, "paused the previously-announced changes") and, on 7 Oct 2026, that Max and Team plans "now include monthly API credits" for the SDK "when you run them with an API key". xAI's terms could not be found (**UNVERIFIED**). Whether Steward, a local open-source app, falls on the permitted side of each line is a legal question: **UNVERIFIED**, see §5.1.
7. **Recommendation** (§4.6): add a `HarnessAgent` (an `AbstractAgent` that emits AG-UI events) with one ACP client as the primary integration, a direct Agent SDK path for Claude only if the ACP adapter proves too lossy, and a Codex app-server client ported from Happy. Route every `request_permission` / approval request through `governance.execute` with a parking executor, run the harness inside the agent's computer workspace, and let the Steward agent delegate to a harness through a governed `delegate_task` tool that produces `SUBAGENT_*` events. Default to API keys; let the person opt into a vendor login only through the vendor's own unmodified binary and flow, never a token Steward collects.

### 1.1 Claude Code (`src/claude/**`)

**Two run modes, one loop.** `loop.ts` (117) alternates `claudeLocalLauncher` and `claudeRemoteLauncher`; the app sees `sendSessionEvent({ type: 'switch', mode })` and `agentState.controlledByUser` (`runClaude.ts:947-953`). Local mode spawns the real `claude` binary in the person's terminal through `scripts/claude_local_launcher.cjs`, adding `--resume <id>` and `--settings <hook file>` (`claudeLocal.ts:215-249`); the phone then only watches. Remote mode drives the Agent SDK.

**The SDK call** (`sdk/query.ts`, 85): maps Happy's `QueryOptions` onto the official `Options` — `cwd, resume, continue, model, fallbackModel, maxTurns, permissionMode, allowedTools, disallowedTools, mcpServers, plugins, systemPrompt (preset claude_code + append), settings, strictMcpConfig, effort, abortController, canUseTool`. It also sets `CLAUDE_CODE_ENTRYPOINT=remote_mobile` so Happy sessions stay visible in `claude --resume` (`sdk/happyEntrypoint.ts`). The prompt is a `PushableAsyncIterable<SDKUserMessage>`: one `query()` call per process lifetime, with later user turns pushed into the iterable after each `result` message (`claudeRemote.ts:166-178, 356-368`).

**Session discovery and resume.** A new session id arrives in the `system/init` message; Happy then waits up to 30 s for `~/.claude/projects/<cwd>/<id>.jsonl` to exist (`claudeRemote.ts:283-317`). A separate **SessionStart hook** (`generateHookSettings.ts`, `startHookServer.ts`: a loopback HTTP server, `POST /hook/session-start`) tells this exact process which session the binary opened, which handles `--continue`, `/compact` forks and double-escape forks without file-watch races. `sessionScanner.ts` (294) tails the JSONL and emits each `RawJSONLines` entry once, skipping `file-history-snapshot`, `change`, `queue-operation`. `claudeSessionFork.ts` (219) copies a transcript to a new UUID, optionally truncated at a message, so "duplicate from here" is `claude --resume <copy>`. Usage comes from `rate_limit_event` messages (`utils/usageLimits.ts`, 167) into `agentState.usageLimits`.

**Hooks.** Only `SessionStart` is used. No `PreToolUse`/`PostToolUse`; permission goes through `canUseTool`, not hooks.

**Happy's own MCP server** (`utils/startHappyServer.ts`, 115): a stateless Streamable-HTTP MCP on loopback with one tool, `change_title`, passed as `mcpServers.happy` and allow-listed as `mcp__happy__change_title`. The same pattern would let Steward hand its governed tools to a harness (§4.6).

**Permissions** (`utils/permissionHandler.ts`, 457). `handleToolCall` is the `canUseTool` callback:
- id = `agentID:toolUseID` for subagent calls, else `toolUseID` (`:177-179`); the raw `toolUseId` is kept so the app can attach the card to the tool call.
- `AskUserQuestion` and `ExitPlanMode` always ask, even in bypass mode (`:143-147, 170-173`).
- allow-lists: a `Set` of tool names and `Bash(cmd)` / `Bash(prefix:*)` literal and prefix sets (`:150-165, 253-279`).
- modes: `bypassPermissions`/`yolo` → allow; `acceptEdits` + edit tool → allow; `plan` + non-dangerous → allow (`:179-193`). `getToolDescriptor` classifies tools as edit/dangerous/exitPlan.
- otherwise: push notification, then `agentState.requests[id] = { tool, arguments, createdAt, toolUseId? }`, then wait on a promise; the SDK's `AbortSignal` rejects it (`:199-250`).
- the answer is RPC `permission` with `{ id, approved, reason?, mode?, allowTools?, updatedInput? }` (`:17-25`). Approved → `{ behavior: 'allow', updatedInput }`; denied → `{ behavior: 'deny', message }` with a fixed "STOP what you are doing" message (`:129-141`). `ExitPlanMode` approval also switches the live query's mode via `query.setPermissionMode` (`:110-128`). The request moves to `completedRequests[id] = { status: approved|denied|canceled, reason, mode, allowedTools }` (`:313-337`).
- `utils/permissionMode.ts` (162): Happy's 8 modes (`auto default acceptEdits bypassPermissions plan read-only safe-yolo yolo`) collapse to the SDK's 5; **when Happy's sandbox is on, the mode is forced to `bypassPermissions`** (`applySandboxPermissionPolicy`), i.e. sandbox replaces prompts.

**Normalisation** (`utils/sessionProtocolMapper.ts`, 709): `RawJSONLines` → `SessionEnvelope[]` with `text` (thinking flag), `tool-call-start/end`, `turn-start/end`, `start/stop`. Subagents: `parent_tool_use_id` → a cuid2 `subagent` id; the parent `Task` tool call is hidden; messages are buffered until the subagent is "started". `sdkToLogConverter.ts` (351) turns SDK messages into the same JSONL shape so remote mode and local mode feed one mapper.

### 1.2 Codex (`src/codex/**`)

**Why hand-rolled.** The header of `codexAppServerClient.ts:7-13`: `@openai/codex-sdk` "only wraps `codex exec` (non-interactive, fire-and-forget). It has NO support for `app-server`, interactive approvals, or bidirectional JSON-RPC." Still true of `@openai/codex-sdk` 0.165.0 (its README is threads over `codex exec`, no approval callback). The types in `codexAppServerTypes.ts` (321) are "cherry-picked from `codex app-server generate-ts` (Codex 0.107.0)"; the generator is the official binding route, there is no npm protocol package (`@openai/codex-app-server-protocol` and `@openai/codex-protocol` are 404).

**Spawn and handshake** (`:608-700`): `codex app-server --listen stdio://` via cross-spawn, `RUST_LOG=codex_core::rollout::list=off`; with Happy's sandbox the command becomes `sh -c <sandbox-wrapped>` and `CODEX_SANDBOX=seatbelt`. `initialize { clientInfo: { name: 'happy-codex' }, capabilities: { experimentalApi: true } }`. Requires codex-cli ≥ 0.153.0.

**Client → server methods used**: `thread/start`, `thread/resume`, `thread/fork`, `thread/read`, `thread/rollback { numTurns }`, `thread/goal/set|clear`, `turn/start`, `turn/interrupt`. `thread/start` params (`:796-811`): `model, cwd, approvalPolicy, sandbox, config: { mcp_servers }, persistExtendedHistory: true`. `turn/start` carries `input: InputItem[]` (text, image, localImage), `approvalPolicy`, `sandboxPolicy` (`workspaceWrite | dangerFullAccess | readOnly`, `:1115-1121`), `model`, `effort`, `summary`.

**Server → client notifications**: v2 `thread/started`, `turn/started`, `turn/completed`, `item/started`, `item/completed`, `thread/status/changed`, `thread/tokenUsage/updated`, `thread/goal/updated|cleared`, `mcpServer/startupStatus/updated`; and the legacy `codex/event { msg: { type } }` stream with `task_started, agent_message, agent_reasoning(_delta), exec_command_begin/end, patch_apply_begin/end, token_count, task_complete, turn_aborted, collab_agent_begin/end, subagent_activity`. Items (`ThreadItem`, types `:63-96`): `userMessage, agentMessage, reasoning, commandExecution, fileChange, mcpToolCall, collabAgentToolCall { tool: spawnAgent|sendInput|resumeAgent|wait|closeAgent, receiverThreadIds, agentsStates }, subAgentActivity`. Codex item ids are per-thread counters, so the client scopes them as `threadId:itemId` (`:85-87`).

**Approvals** (server → client requests, `handleServerRequest`, `:1394-1495`):
- `item/commandExecution/requestApproval` (legacy `execCommandApproval`): `{ threadId, turnId, itemId, approvalId?, command[], cwd, reason }` → answered `{ decision: accept | acceptForSession | decline | cancel }` (legacy `approved | approved_for_session | denied | abort`) or `{ approved_execpolicy_amendment }` (`:1329-1348`).
- `item/fileChange/requestApproval` (legacy `applyPatchApproval`): `{ itemId, fileChanges: Record<path, add|delete|update{unified_diff}>, reason, grantRoot }` → same decisions.
- `mcpServer/elicitation/request`: `{ serverName, message, _meta.tool_params }` → `{ action: accept|decline|cancel, content }`; the tool name is regex-parsed out of `message` (`:1352-1358`).
- OpenAI's current doc (learn.chatgpt.com/docs/app-server) adds `item/permissions/requestApproval` (network/filesystem grants with `scope: session|turn`), `item/tool/requestUserInput`, `item/tool/call` (dynamic tools, experimental) and `account/chatgptAuthTokens/refresh`. Happy does not handle these (unknown requests get `{}` back, `:1491-1494`).
- `ApprovalHandler` input (`:64-79`) is `{ type: exec|patch|mcp, callId, itemId, threadId, turnId, approvalId, command, cwd, fileChanges, reason, toolName, input, serverName, message }`. `runCodex.ts:645-683` names them `CodexBash { command, cwd }`, `CodexPatch { changes }`, `<mcp tool> { input }` and hands them to `CodexPermissionHandler` (116, extends `BasePermissionHandler`), which auto-approves `change_title` and otherwise parks in `agentState.requests`. A second concurrent approval for the same item gets an `:approvalId` suffix so it never overwrites a pending promise (`:1497-1505`). No handler ⇒ `denied`.

**Policy** (`executionPolicy.ts`, 76): Happy mode → `(approvalPolicy, sandbox)`: `auto → (on-request, workspace-write)`, `default → (untrusted, workspace-write)`, `read-only → (never, read-only)`, `safe-yolo → (never, workspace-write)`, `yolo → (never, danger-full-access)`. With Happy's own sandbox: `(never, danger-full-access)` and auto-approve everything, i.e. Codex's sandbox is switched off in favour of Happy's.

**Turn driving** (`runCodex.ts`, 1,093): `client.connect()`; resume or `startThread`; per user message `turn/start`; a pending-turn promise resolves on `turn/completed` or `task_complete`/`turn_aborted`; `turn/interrupt` with a 3 s grace then force-restart of the app-server (`:1033-1064`). The `happy` MCP server reaches Codex through `bin/happy-mcp.mjs`, a stdio→HTTP bridge (`happyMcpStdioBridge.ts`, 106), configured as `config.mcp_servers.happy = { command: node, args: [bridge, --url] }` (`runCodex.ts:817-822`).

**Normalisation** (`utils/sessionProtocolMapper.ts`, 1,406): items and legacy events → envelopes; `codexItemId` on each so the app can "duplicate from message" via `thread/rollback`; collab subagent threads become `subagent` ids with titles; `thread/tokenUsage/updated` → `usage`.

### 1.3 ACP agents (`src/agent/acp/**`) and `happy gemini`

**Configured agents** (`acpAgentConfig.ts`, 53): `gemini → gemini --experimental-acp`, `opencode → opencode acp`; `happy acp -- <cmd> [args]` runs anything; unknown names are spawned as-is. The daemon cannot start `acp` sessions (its enum is `claude | codex | gemini | openclaw | agy`).

**Driving a session** (`AcpBackend.ts`, 1,336): `child_process.spawn(cmd, args, stdio pipe)`; stdout is filtered to JSON-only lines (`DefaultTransport.ts:59-78`); SDK `ndJsonStream` + `new ClientSideConnection(client, stream)` (`:560, 709-712`). `initialize { protocolVersion: 1, clientCapabilities: { fs: { readTextFile: false, writeTextFile: false } } }` with 3 retries (`:715-772`); `newSession { cwd, mcpServers: [{ name: 'happy', command, args, env }] }` (`:792-833`); `prompt { sessionId, prompt: [{ type: 'text', text }] }` (text only, `:1066-1077`); `cancel`; `setSessionConfigOption` / `setSessionMode` / `unstable_setSessionModel` for mode and model switching. The client implements only `sessionUpdate` and `requestPermission`; `readTextFile`, `writeTextFile`, `createTerminal` are not implemented.

**Session updates handled** (`sessionUpdateHandlers.ts`, 558): `agent_message_chunk` → `model-output` (a `**Title**\n` prefix is reclassified as thinking); `agent_thought_chunk` → thinking; `tool_call` / `tool_call_update` → `tool-call` / `tool-result` with the ACP **`kind`** used as the tool name (the real name is stored but never emitted, `:250-254` vs `:309-314`); `available_commands_update`, `config_option_update`, `current_mode_update` → metadata. A spec `plan` update (`entries`) falls through unhandled; `user_message_chunk` is not handled (**UNVERIFIED** against the 0.14.1 types). Turn end is heuristic: a 500 ms idle timer after the last chunk with no active tools (`:153-200`), plus a 5-minute cap in `runAcp.ts:33`.

**`requestPermission`** (`AcpBackend.ts:567-705`): reads `toolCall.id|kind|toolName|input|arguments|content` and `options[{ optionId, name, kind }]`; emits `permission-request { id, reason: toolName, payload }`; blocks on `permissionHandler.handleToolCall(id, toolName, input)` → `{ decision }`; then maps **by option id or name, ignoring `kind`**: `approved_for_session` → `proceed_always` / name contains "always"; `approved` → `proceed_once` / "once" / `options[0]`; `denied|abort` → `cancel` or the literal string `'cancel'`. Always responds `{ outcome: { outcome: 'selected', optionId } }`; the spec's `cancelled` outcome is never used. The spec fields are `toolCall.toolCallId` and `rawInput`, so a strictly conforming agent gets a random permission id and `content` instead of input (**UNVERIFIED**).

**`happy gemini`** (`runGemini.ts`, 1,337; `factories/gemini.ts`, 187; `GeminiTransport.ts`, 334) is the same `AcpBackend` with: API key from Happy's cloud vendor token, `~/.gemini/*`, gcloud ADC, or `GEMINI_API_KEY`; model via `GEMINI_MODEL`; a 120 s init timeout; 404/429 stderr detection; `GeminiPermissionHandler` auto-approving by mode (`yolo` all, `safe-yolo`/`read-only` unless the name contains write/edit/create/delete/patch/bash/shell/execute) and a fixed safe list (`change_title, think, save_memory, …`); and legacy `sendAgentMessage('gemini', …)` messages rather than envelopes. `src/index.ts:334-335` prints a deprecation notice pointing at `happy agy`.

### 1.4 Antigravity (`src/agy/**`, 808)

`agy` is found via `HAPPY_AGY_PATH`, `PATH`, or `~/.local/bin/agy`. One process per turn: `agy [--conversation <id>] [--model "<name>"] (--dangerously-skip-permissions | --sandbox) --add-dir <cwd> --print-timeout 10m --print "<prompt>"` (`cliArgs.ts:43-66`); stdout chunks become `model-output`; exit 0 → idle, else error; SIGKILL watchdog. **There is no tool or permission stream at all.** Modes `yolo, safe-yolo, bypassPermissions, acceptEdits` → skip permissions; everything else → `--sandbox` and agy's own `settings.json`. This is the least governable integration and a template for what Steward must not do.

### 1.5 OpenClaw (`src/openclaw/**`, 1,498)

A client of the "OpenClaw gateway protocol (v3)": the gateway URL comes from `--gateway-url`, `OPENCLAW_GATEWAY_URL`, `openclaw status --json` or the configured port; auth is a gateway token or password plus an Ed25519 device identity (stored under `~/openclaw/`, not `~/.openclaw/`) that signs a `connect.challenge` nonce and requests scopes `operator.admin, operator.approvals, operator.pairing` (`OpenClawSocket.ts:282-388`). Turns are `chat.send` and `chat` events (`started | thinking | delta | tool | final | error`); `delta` text is cumulative and diffed. Tool events have no result and **no approvals are handled** although the scope is requested; the only gate is device pairing.

### 1.6 Permission prompts → Steward approvals

What each harness gives you, and how it lands on `Approval { id, toolCallId, tool { name, kind, surface, source }, args, target, canAlways, answer: once | always | refuse }` (`packages/shared/src/governance.ts:130-152`):

| Harness | Prompt arrives as | Fields for `GateCall` | Answers it accepts | Steward answer mapping |
| --- | --- | --- | --- | --- |
| Claude Agent SDK | `canUseTool(toolName, input, { toolUseID, agentID, signal })` | `tool.name` = SDK tool (`Bash`, `Edit`, `Write`, `WebFetch`, `mcp__…`), `args` = input, `target.command` = `input.command`, `target.path` = `input.file_path`; kind from a descriptor table like `getToolDescriptor.ts` | `{ behavior: 'allow', updatedInput }`, `{ behavior: 'deny', message }`; plus `query.setPermissionMode` | once/always → allow (always = Steward rule, never SDK mode); refuse → deny with Steward's message |
| Codex app-server | `item/commandExecution/requestApproval { command[], cwd, reason }`, `item/fileChange/requestApproval { fileChanges }`, `mcpServer/elicitation/request`, (`item/permissions/requestApproval`) | `shell` kind with `target.command = command.join(' ')`; `write` kind with `target.path` per changed file; `mcp` with `{ server, tool }` | `accept`, `acceptForSession`, `decline`, `cancel`, execpolicy amendment | once → `accept`; always → `acceptForSession` **only when `canAlways`**; refuse → `decline`; run cancelled → `cancel` |
| ACP v1 | `session/request_permission { sessionId, toolCall { toolCallId, title, kind, rawInput, locations }, options[{ optionId, name, kind }] }` | `tool.name` = `title`/`name`, kind from ACP `ToolKind` (`read→read`, `edit/move→write`, `delete→delete`, `execute→shell`, `fetch/search→read`, `think→ui`, `other→write`), `target.path` from `locations`, `target.command` from `rawInput` | `{ outcome: { outcome: 'selected', optionId } }` or `{ outcome: 'cancelled' }` | pick the option whose `kind` matches: once → `allow_once`; always → `allow_always` if `canAlways` else `allow_once`; refuse → `reject_once`; cancelled run → `cancelled` |
| `agy`, OpenClaw | nothing | — | — | not integrable as governed harnesses; run only inside the computer sandbox with the vendor's own prompts off, or not at all |

Two behaviours in Happy that Steward should keep: the request id must equal the tool-call id the UI already shows (`agentID:toolUseID`, `threadId:itemId`) so the card attaches to the call; and a reset/abort must move every pending request to `completedRequests` with `status: 'canceled'` and reject the awaiting promise, otherwise the harness hangs (`permissionHandler.ts:286-311`).

## 2. Happy Agent (`happy-agent-runtime`): multi-provider, Grok, subscriptions, subagents, multiplayer

Sizes (non-test TS): `happy-providers` 29,905 lines in 338 files; `happy-agent-modules` 194,735; `happy-agent-client` 17,970; `happy-agent` 10,060; `happy-agent-base` 12,741; `happy-agent-compute` 15,385; `happy-agent-supervisor` 281 TS plus ~9.4k Rust. `happy-desktop` is ~279k TS/TSX (`happy-desktop-ui` 136,628; `-state` 69,505; `-electron` 37,462; `-app` 21,501).

### 2.1 What "multi-provider" means here

Happy Agent is a harness of its own, not a wrapper. The interface is `BaseProvider.session(id, options) → BaseSession.run(ctx, request) → SessionStream` (`happy-providers/sources/core/BaseProvider.ts`, 23; `BaseSession.ts`, 20; `docs/architecture.md:216-220`), and `architecture.md:240-244` states the goal: "The package's entire purpose is that a Happy Agent request looks like the native client's request". Providers by static `name`: `claude` (`vendors/anthropic/AnthropicProvider.ts`, 71, which routes a Claude credential to `vendors/claude/ClaudeProvider.ts`, 83, and a Bedrock credential to `vendors/bedrock/`), `codex` (`vendors/codex/CodexProvider.ts`, 183), `grok` (`vendors/grok/GrokProvider.ts`, 63, extending `protocol/responses/ResponsesProvider.ts`), `openai_compatible` (171), `kimi` and `glm` (Bedrock-only), and `acp` (`protocol/acp/AcpProvider.ts`, 109; 2,078 lines in `protocol/acp/`) plus "foreign agents" that run the vendor harnesses themselves: `vendors/claudeAgent/claudeAgentConnect.ts` (399), `vendors/codexAppServer/codexAppServerConnect.ts` (494), `vendors/foreignAgents/` (530). Gemini is only a credential for tools (`vendors/gemini/GeminiApiKeyCredential.ts`, 31), not a chat provider.

A model id picks its family by prefix (`core/providerModelFamily.ts`, 14): `anthropic/ → claude`, `openai/ → codex`, `xai/ → grok`, `moonshotai/ → kimi`, `zai/ → glm`, and `claude-code/ | codex-cli/ | antigravity/ | opencode/ | acp/ → foreign`. The catalogue is hard-coded ("Happy Agent never asks a vendor which models exist", `happy-agent-modules/sources/config/impl/agentCatalog.ts:191-222`): `openai/gpt-6.1-sol|terra, gpt-6-astra|sol|luna`; `anthropic/opus-5-5, sonnet-5-5, haiku-5-5, fable-5-1, opus-5, sonnet-5, fable-5, opus-4-8`; `xai/grok-4.7, grok-4.6, grok-build, grok-4.5, grok-composer-2.5-fast`. Wire ids are rewritten per vendor (`anthropic/opus-5-5 → claude-opus-5-5[1m]`, `resolveClaudeModelId.ts`; `xai/` prefix stripped, `resolveGrokModelId.ts`; `tests/modelIds.test.ts`, 60).

"Model-native prompts and tools": `systemPrompt/impl/systemPromptForModel.ts` (78) picks a prompt written for the exact model, else the vendor's (`codex_agent_instructions` 302 lines, `grok_4_5_system_prompt` 36, `claude_opus_5_system_prompt`); `compute/tools/assembleComputeTools.ts` (43) picks the vendor's fixed tool set: `compute/tools/claude/` (Bash, Read, Edit, Write, Glob, Grep…; 1,256 lines), `codex/` (exec_command, apply_patch, write_stdin…; 636), `grok/` (run_terminal_command, read_file, search_replace…; 1,056). The prompt/tool folders under `happy-providers/sources/vendors/*/` are capture assets, "not runtime fallbacks" (`VENDOR_CLAUDE.md:89-92`). "Built on Pi" (README) is a design claim: no Pi package appears in `pnpm-lock.yaml`, and `docs/permissions-and-sandbox.md:179-182` calls the Pi surface "part of the stated model, not of what runs today" (**UNVERIFIED** how much Pi code is inlined).

### 2.3 How a session picks a provider and model

`happy.toml` `[providers.<id>]` (`type, enabled, hidden, include_models/exclude_models, include_subagent_models/exclude_subagent_models`) and `[defaults] provider/model/effort/service_tier/permission_mode` (`docs/configuration.md:565-670`); built-in default `openai/gpt-6.1-sol`, `permissionMode: "auto"` (`ConfigModule.ts:1535`); if the default is not served by an enabled provider "the first available model stands in" (`agentCatalog.ts:256-310`). Every message carries `MessageMode { providerId, providerType?, account?, modelId, effort, serviceTier, permissionMode }` (`happy-agent-client/sources/protocol/common.ts:71-84`), changed with `PUT /v0/agents/:id/draft`; `core/ProviderModelCompatibility.ts` (80) decides whether history survives a switch (claude ↔ claude/foreign, codex ↔ codex/foreign, grok ↔ grok, bedrock within a region, `openai_compatible` never), and an incompatible switch starts a fresh context with a notice (`modelSwitch/ModelSwitchModule.ts`, 121). There is no cross-vendor fallback; only round-robin inside a smart pool.

### 2.4 "Delegate to subagents on any of them"

`docs/agents-and-collaboration.md` (394) describes vendor-shaped tools (Claude `Agent`/`SendMessage`, Codex `spawn_agent`, Grok `spawn_subagent`, depth 3, 8 concurrent); none of those names is registered at runtime, they exist only as capture assets. The live module is `happy-agent-modules/sources/collaboration/` (`CollaborationModule.ts` 1,205; `README.md` 239): tools `create_agent { title, model, effort, harness?, provider?, serviceTier?, text }` (model and effort required; checked against the subagent model lists; provider defaults to the creator's if it serves the model, `tools/create_agent.ts:47-58`; the choice is fixed at creation), `send_agent_message`, `interrupt_agent` ("Aborts a collaborator subtree and hard-kills its processes"), `archive_agent`, `agent_options`, and `subtasks/tools/create_subtask.ts`. **Results come back asynchronously as a steering message** into the parent's next inference: "Collaborator b7c1 finished working. Its answer follows, verbatim." (or "…stopped without answering. It failed with, verbatim."), tagged `collaboration.kind = "subagent_report"` with `fromAgentId` (`collaboration/README.md:27-133`). Limits: `maxCollaborationDepth: 3`, `maxCollaborators: 5` per root tree, finished ones still counting (`ConfigModule.ts:1593-1594`); `POST /v0/agents/:id/abort` "immediately aborts this and every descendant run". Usage: `usage/UsageModule.ts` (1,368) records per run by provider and model, `get_agent_tree_usage` sums the subtree, the client's agent object exposes `totalTokens` and `subagents { running, total }`; `costUsd` is always written as `null` (`usage/impl/usageDatabase.ts:125, 190`), so there is no money figure anywhere.

### 2.5 "Natively multiplayer"

The phrase is on `happy/README.md:32-33`: "Invite a colleague or a friend into the session. You both watch the same agent work, and either of you can steer it." The implementation is team mode (`docs/team-mode.md`, 399; `docs/happy-teams.md`, 83): one daemon serves a WorkOS organisation over HTTP, SSE and WebSocket on TCP, optionally through Tailcat (WireGuard, NAT traversal, DERP fallback); identity is a WorkOS RS256 access token checked locally (`org_id, sub, client_id`) or an enterprise JWT, one durable CUID2 user per identity with `isOwner`; the `team` module "announces the human sender to the model" so several people write into one conversation (`team/README.md`, 35); question answers are "first-write-wins across clients"; drafts sync (`EVENTS.md:74-92`); agents message agents with `send_agent_message`, across workspaces when `features.cross_workspace` is on; shared surfaces (todo lists, documents, calendars; `surfaces/README.md`, 79). Provider access is the service account's own logins. Standalone mode is "HTTP/1.1 over a Unix domain socket. There is no TCP listener" (socket 0600, 43-character bearer token in a 0600 file; `happy-agent/API.md` "Transport"). Per-session access rules between members are **UNVERIFIED**.

### 2.6 Permissions and sandbox in Happy Agent (the design Steward must not copy)

Modes `read_only | workspace_write | auto | full_access`, default `auto` (`happy-agent-base/sources/AgentPermissionMode.ts`, 57). **Auto mode never prompts the person**: a read-only reviewer model ("Codex's Guardian policy, plus the user's global `SECURITY.md`") returns allow or deny, with a circuit breaker after 3 consecutive refusals or 10 in the last 50 (`docs/permissions-and-sandbox.md:91-106`). Events: `permission_review { toolCallId, action, decision: allow | ask, reason, risk, userAuthorization }`, `permission_action_denied | unproven | out_of_mode`, `permission_turn_stopped` (`permissions/PermissionEvent.ts`, 138; `EVENTS.md:193`). Escalation is a per-tool flag (`sandbox_permissions: "require_escalated"`, Claude `dangerouslyDisableSandbox: true`). The only prompt a client answers is a `Question { id, agentId, runId, status, questions[] }` (`happy-agent-client/sources/protocol/questions.ts`, 111; `POST /v0/agents/:id/question/:qid/answer`, a second answer is 409), including `QuestionPermissionRequest { source: "mcp_elicitation" }`. Sandbox: the docs say Seatbelt / Bubblewrap / `@anthropic-ai/sandbox-runtime`; the code is a Rust supervisor (`happy-agent-supervisor/README.md:1-36`: Linux user/mount/PID namespaces, seccomp, no capabilities; macOS in-process Seatbelt; Windows restricted tokens and firewall) with policies "adapted from OpenAI Codex" under Apache-2.0 (`THIRD-PARTY-NOTICES.md:13-23`). In one line: Happy Agent replaces the person's approval with a model's; Steward's gateway is the opposite design, and that is the thing to keep.

## 3. The common session abstraction, and how close it is to AG-UI

### 3.1 What Happy normalises to

**`happy-wire/src/sessionProtocol.ts` (174)**: `SessionEnvelope { id, time, role: 'user'|'agent', turn?, subagent? (cuid2), claudeUuid?, codexItemId?, usage?: SessionUsage, ev }` with `ev.t ∈ text { text, thinking? } | service { text } | tool-call-start { call, name, title, description, args } | tool-call-end { call } | file { ref, name, size, mimeType, image } | turn-start | start { title? } | turn-end { status: completed|failed|cancelled } | stop`. The file header: "UNDER REVIEW - NEEDS MORE CAREFUL DESIGN … look at how pi.dev standardizes their agent protocol … Types are kept here for reference but are frozen. Do not add new consumers." On the wire it is the plaintext of an encrypted `SessionMessage { id, seq, localId, content: { t: 'encrypted', c } }` whose decrypted body is `{ role: 'session', content: envelope, meta }` (`messages.ts:24-36`). Notice what is **not** in it: tool results (`tool-call-end` carries only `call`; `AcpSessionManager.ts:172-179` drops the content), permission requests (they live in `agentState.requests`), state, and token usage except as an optional side field.

### 3.3 `@ag-ui/claude-agent-sdk` (0.0.8, MIT) — the existing Claude→AG-UI adapter

`ag-ui/integrations/claude-agent-sdk/typescript` (5,074 lines; `adapter.ts` 1,399, `utils.ts` 957, `native-recovery.ts` 719, `native-history.ts` 582, `recovery.ts` 503). `ClaudeAgentAdapterConfig = AgentConfig & Options & { nativeChildRecovery?, sessionRecovery?, maxSessions?, sessionTtlMs?, queryTimeoutMs? }` (`types.ts:54-66`), so it takes the whole SDK `Options`. For Steward it is a starting point for the event mapping, not for governance.

### 4.5 Should ACP be Steward's single integration point?

**Yes, as the default, with two carve-outs.** Reasons for: one client (`ClientSideConnection` over stdio) covers Gemini CLI natively and Claude/Codex through Zed's maintained adapters, plus Copilot, Pi, OpenCode, Goose, Cursor, Kiro, Qwen Code, Mistral Vibe and ~40 more (agentclientprotocol.com/overview/agents, fetched 27 Oct 2026; Happy's mobile app is itself listed as an ACP client); the permission request is already the right shape (`options[].kind`, `ToolKind`, `locations`, `rawInput`, `cancelled` outcome) and the spec says "Clients MAY automatically allow or reject requests based on user settings", which is Steward's policy gateway; `tool_call` updates carry `kind`, `locations` and `content` (diffs, terminals) for the record; and the SDK is Apache-2.0 with a stable v1.

Carve-outs: (a) ACP v1 has **no token-usage or cost events** and no "always allow" memory on the client side (the agent owns remembered decisions, so Steward should always answer `allow_once` and keep its own "always" rules); (b) adapter fidelity: `claude-agent-acp` is a wrapper over the Agent SDK, so subagent (`Task`) structure, `rate_limit_event`, compaction and plan mode arrive only as far as the adapter forwards them (**UNVERIFIED** how much it forwards), and `codex-acp` lags the app-server protocol (0.16.0 is from June; the app-server has since added `item/permissions/requestApproval` and `turn/steer`). So keep a direct Codex app-server client (ported from Happy, §4.1) for Codex, and keep a direct Agent SDK path for Claude only if the ACP adapter proves too lossy. Everything else: ACP.

### 4.6 Recommended shape for Steward

```
packages/harnesses/
  src/harness-agent.ts        HarnessAgent extends AbstractAgent: run(input) → Observable<BaseEvent>
                              owns: process per thread (cwd = computers/<agent>/workspace), resume handle in SQLite,
                              event mapping, parking of permission requests, abort → cancel
  src/acp/                    ACP client (spawn, ndjson, initialize/newSession/loadSession/prompt/cancel,
                              sessionUpdate → AG-UI, requestPermission → gateway)   ~900 lines
  src/codex/                  app-server client (ported) + mapping                   ~1,300 lines
  src/claude/                 optional: Agent SDK + @ag-ui/claude-agent-sdk mapping + canUseTool → gateway
  src/registry.ts             harness profiles: { id, kind: acp|codex|claude, command, args, env, models[] }
```

- **One gateway.** Every `request_permission` / `requestApproval` / `canUseTool` becomes a `GateCall` with `tool.source = 'harness:<id>'`, `kind` from §1.6, `target` from paths/commands, `tainted` true (the harness read files and ran commands) and goes through `governance.execute(call, executor)`. `allow` → answer the harness at once; `deny` → answer refuse with Steward's message; `parked` → emit `CUSTOM steward.approval.requested` + `RUN_FINISHED { outcome: interrupt }`, **keep the harness process and its pending request alive**, and persist `{ threadId, harnessSessionId, requestId }`; the resume run calls `governance.resume`, answers the harness and continues streaming. The harness's own prompt system is set to "ask for everything" (Codex `approvalPolicy: 'untrusted'`; Claude `permissionMode: 'default'` with an empty allow-list; ACP agents in their default mode) so the gateway is the only path to act. Never pass `bypassPermissions`, `danger-full-access` or `--dangerously-skip-permissions`.
- **Tools the harness cannot see.** Steward's mail, calendar, browser and MCP tools are not given to the harness. If a coding harness needs one, expose it the way Happy exposes `change_title`: a loopback MCP server (Streamable HTTP, like `startHappyServer.ts`) whose tool handlers call `governance.execute` themselves, so even harness-originated calls are governed and recorded.
- **Per-conversation choice.** Add `harness?: string` next to `model?` in `agents.yaml` profiles (`packages/shared/src/domain.ts:199-200`) and let a thread pick an agent id; the web app already switches with `useAgent({ agentId, threadId })`. `AgentHost.configure` builds a `HarnessAgent` for profiles with `harness` set, alongside `BuiltInAgent`s.
- **Delegation.** Give the Steward agent a governed `delegate_task { agentId, task, cwd? }` tool (kind `write`, surface `task`). Its executor starts a sub-run on the target agent through the runner (the same path `server-runs.ts` uses for routines), emits `SUBAGENT_STARTED { subagentRunId, name }`, forwards the child's events with `subagentRunId` set, and returns the child's final text as the `TOOL_CALL_RESULT` (wrapped untrusted). Approvals inside the child interrupt the parent run with `interrupts[].subagentRunId` set, the way Happy scopes ids as `agentID:toolUseID`. Nested delegation depth 1, concurrency 2, both configurable.
- **Cost.** Emit `RUN_FINISHED.usage: TokenUsage[]` from Codex `thread/tokenUsage/updated`, Claude `result.usage`, and `provider: 'harness:<id>'` with zeros for ACP agents that report nothing; show it in the record. Subscription-backed runs cannot be priced; label them "included in <vendor> plan" and never estimate money.
- **Sandbox.** `cwd` is the agent's workspace; env is the same allow-list the shell uses; the harness's own sandbox stays on (`workspace-write`); Steward's loopback/private-host rules do not apply to the harness's network (it must reach its vendor), so record that exception in the policy.

## 5. Risks

### 5.1 Licence and terms of the subscriptions

- **Code licences are fine**: Happy (MIT), ACP SDK and Zed adapters (Apache-2.0), Codex CLI/SDK (Apache-2.0), AG-UI (MIT), Pi (MIT). The Claude Agent SDK and Claude Code binary are **proprietary** ("governed by Anthropic's Commercial Terms of Service"); Steward would depend on them as external binaries the person installs, as Happy does.
- **Anthropic** (code.claude.com/docs/en/legal-and-compliance, fetched 27 Oct 2026, quoted verbatim): OAuth "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications"; developers "including those using the Agent SDK, should use API key authentication"; "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens"; and "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code", subject to: "The Claude Code binary must not be modified" and "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf." Press reports (The Register 20 Feb 2026 and others) describe server-side enforcement from January 2026 and, from April 2026, third-party harness usage no longer covered by plan limits. **UNVERIFIED legal conclusion**: a Steward that spawns the unmodified `claude` binary (directly or through the Agent SDK / `claude-agent-acp`) with the person's own login, on the person's own machine, looks like the permitted "end user signing in to the unmodified Claude Code binary"; a Steward that reads `~/.claude/.credentials.json` and calls `api.anthropic.com` itself (what a Pi-style harness does) looks like the prohibited "intermediate … session tokens". Steward should do the former only, default to API keys, and never touch the credential file. Happy's own README says the daemon needs "keychain access, OAuth credentials" and suggests exporting the token as `CLAUDE_CODE_OAUTH_TOKEN` for launchd (`happy-cli/README.md:68, 86`); Happy Agent goes further and reads the keychain item or `.credentials.json` itself, passes the token to the SDK binary in env, and calls `api.anthropic.com/api/oauth/usage` with a `claude-cli/2.0.0` user agent (§2.2). Do not copy any of that. The contradiction between the legal page and the support article Happy cites ("third-party app usage still draw from your subscription limits", 15 June 2026; Max/Team "monthly API credits" for the SDK "with an API key", 7 Oct 2026) is real and unresolved here: **UNVERIFIED**, and the legal page carries the enforcement language.
- **OpenAI** (learn.chatgpt.com/docs/app-server and /docs/auth, fetched 27 Oct 2026): "The app-server command and WebSocket transport are experimental and aren't supported for production workloads"; "App-server authentication has never been permitted for commercial or hosted services"; "we recommend migrating to Sign in with ChatGPT" for "local or open-source apps"; an experimental `chatgptAuthTokens` mode exists for "Host apps that already own a user's ChatGPT auth lifecycle"; `~/.codex/auth.json` is plaintext, "treat … like a password". The Sign in with ChatGPT page says "eligible ChatGPT Plus and Pro subscribers can also choose to use their ChatGPT plan for AI requests" in participating apps, with per-app caps in ChatGPT settings, and lists "open-source integrations". **UNVERIFIED**: whether Steward qualifies as a "local or open-source app" without registration; the safe path is spawning `codex app-server` with the login Codex itself holds (never reading `auth.json`), and investigating the Sign in with ChatGPT developer programme. What Happy Agent does instead, reading `auth.json`, calling `chatgpt.com/backend-api/codex/responses` with `originator: codex_exec` and a user agent copied from `codex --version`, and refreshing with Codex's own OAuth client id (§2.2), is precisely the pattern the `chatgptAuthTokens` text is about and should not be Steward's model.
- **xAI**: no terms found; Grok Build beta appears tied to SuperGrok tiers and uses a browser OAuth on first launch (secondary sources only). Grok Build's code is Apache-2.0 (`xai-org/grok-build`, per Happy's `THIRD-PARTY-NOTICES.md`), but the endpoint Happy uses, `cli-chat-proxy.grok.com`, is a consumer proxy that rejects old client versions with HTTP 426 and bills "free grok build usage" (§2.2), which signals it is meant for the CLI. **UNVERIFIED** entirely. Treat Grok as API-key only (`api.x.ai`, OpenAI-compatible, which Steward's `openai-compatible` provider already covers) until xAI publishes terms.
- **Google**: Gemini CLI is Apache-2.0 and its own login flow; ACP is a documented feature. Lowest risk of the four.
- Product consequence: "reuse your subscriptions" in Steward must mean "run the vendor's own tool, signed in by you", not "Steward signs in for you". The setup checklist should say so, and the model picker should show "via Claude Code (your login)" distinctly from "Anthropic API key".

### 5.2 Security: keeping the gateway the only path to act

- Harnesses have their **own** tools (shell, file edit, web fetch, MCP) and their own permission systems; Happy mostly defers to them (modes, allow-lists, auto-approve by name, sandbox ⇒ no prompts). That is the opposite of Steward's invariant. Mitigations in §4.6: ask-for-everything mode, every prompt through `governance.execute`, no bypass flags, and `tainted: true` on every harness call so `send`/`pay`/`delete`/`shell` always ask.
- **Gaps the gateway cannot see**: a harness's read-only tools (Claude `Read`/`Grep`, Codex sandboxed reads, ACP `read`/`search`) run without a prompt in every harness. Steward can see them (ACP `tool_call` updates, Claude `assistant` tool_use blocks) and record them, but not refuse them unless the mode asks for everything, which Claude Code and Codex do not offer for reads. Accept and document: reads inside the workspace are allowed; the workspace must contain nothing the agent should not read.
- **Prompt-injection surface**: Codex `mcpServer/elicitation/request.message` is free text parsed by regex for a tool name (`:1352-1358`); ACP `title`/`name` are "informational only and does not grant authorization" (spec). Steward's `GateCall.tool.name` must come from structured fields (`rawInput`, `command[]`, `fileChanges`), never from titles, and the approval card must show the structured target.
- **Credential files in the workspace**: Happy's sandbox explicitly allows writes to `~/.codex` and `~/.claude` (`sandbox/config.ts:19-27`). Steward must not mount those into the computer workspace; the harness process needs them, the agent's file tools do not.
- **Sandbox-escape by design**: Codex `approvalPolicy: never` + `danger-full-access` when Happy's sandbox is on; `agy --dangerously-skip-permissions`; Claude `bypassPermissions` under sandbox. None of these may exist in Steward's configuration surface, not even behind a flag.
- **Network**: harnesses need their vendor endpoints; Steward's private-host refusal (`STEWARD_ALLOW_PRIVATE_HOSTS`) should still apply to the harness's `WebFetch`-type tools where the harness exposes a host (ACP `fetch` kind with a URL in `rawInput`), and the record should show every host.
- **Process hygiene**: Codex app-server and ACP agents hang when a request is left unanswered; Happy's epoch-guarded reconnect and "move pending to canceled on reset" are the minimum. A harness process that outlives its thread is a leak and a stale permission channel; tie it to the thread and to `AgentHost.configure` generations.

### 5.3 Cost tracking

Token usage is harness-specific (Codex `thread/tokenUsage/updated` and legacy `token_count`; Claude `result.usage` + `rate_limit_event`; ACP v1 nothing; agy nothing). AG-UI's `TokenUsage[]` on `RUN_FINISHED` is the right sink; subscription-backed runs cannot be priced, and Happy's `usageLimits` (plan windows) is a subscription concept Steward should not reproduce. Expect "cost unknown" to be the common case for harness runs.

### 5.4 Maintenance burden

Happy carries ~23k lines of harness code and a changelog full of protocol chases: Codex legacy vs v2 notifications, `approved`/`accept` decision renames, item-id scoping, Claude entrypoint filtering (#1202), mode-default regressions (#1721), Gemini 404/429 quirks, Windows `.cmd` shims. ACP absorbs most of that drift into Zed's adapters; the price is adapter lag (`codex-acp` four months behind the app-server). Budget: ACP client ~900 lines + Codex client ~1,300 lines + harness agent ~400 lines, plus one integration test per harness against a scripted fake (an ndjson fixture process is enough for ACP; Happy's `experiments/` has none worth copying). Pin versions; treat every harness upgrade as a protocol change.
